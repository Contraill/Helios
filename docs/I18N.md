# Language and Localisation

## Supported locales

Helios supports two complete interface locales:

- `en` — English;
- `tr` — Turkish.

Visible copy, accessible names, validation messages, loading/empty/error states, date/number formatting and route metadata all use the same typed locale contract. Scientific values and source identities remain unchanged; only their presentation and explanatory copy are localised.

## Preference and rendering contract

The selected locale is stored in the `helios-locale` cookie for one year. The cookie is read by Server Components and metadata generation, then hydrated into the bounded client locale store. Changing language:

- preserves the current route;
- preserves Explore selection, camera and simulation state;
- refreshes Server Components and metadata;
- updates `<html lang>` to `en-US` or `tr-TR`;
- never changes data freshness, source values or calculations.

English is the deterministic fallback when the cookie is absent or invalid.

## URL and indexing strategy

Helios deliberately keeps one canonical URL per page. Language is a user preference, not a second indexed route tree. Therefore:

- `/body/mars` remains canonical in both interface languages;
- legacy `/planet` and `/object` routes still canonicalise to `/body`;
- sitemap entries are language-neutral;
- no `hreflang` alternates are published without distinct locale URLs;
- social images remain language-neutral while page titles and descriptions follow the request locale.

A future locale-path migration would be a separate routing decision and must preserve the current body, region and legacy compatibility contracts.

## Translation coverage

The EN/TR contract covers:

- global navigation, footer, skip link and error pages;
- home, Explore, Compare, Missions, Data, About and Case Study;
- all Explore docks, summaries, loading and WebGL fallback states;
- 57 body pages, four region pages and eight custom planet compositions;
- remote-data current, stale, fallback, partial, empty and unavailable states;
- metadata, accessible labels, forms, source/provenance labels and locale formatting.

## Translation rules

- Data definitions and uncertainty qualifiers must survive translation.
- `historical`, `latest-available`, `near-live`, `reference` and schematic representation remain distinct.
- A provider or mission proper name is not translated unless the official source uses a localised form.
- Units are formatted at presentation time; source values are not duplicated into locale-specific datasets.
- Missing copy is a release error. English is used only as the invalid/missing-cookie fallback, not as a silent per-field fallback.

## Verification

```bash
pnpm audit:i18n
pnpm audit:editorial
```

The language audit compares catalogue shape, checks required server routes, rejects retired English-only Explore copy and verifies the cookie-backed refresh contract. The editorial audit server-renders both locales across the complete semantic library.
